# План: AI Data Engineering через практический проект

## Цель и формат

Создать AI Usage Telemetry Platform и научиться самостоятельно объяснять, реализовывать и проверять её компоненты. Основной канал работы — текущий чат Codex. Код, план и подтверждённый прогресс храним в этом репозитории для работы с двух компьютеров.

Опираемся на имеющийся опыт DE. Основной фокус: AI API integrations, telemetry, надёжность данных и system design. Требования Itexus и Janea Systems сопоставим с модулями после получения полных текстов вакансий; пока это учебный маршрут, а не проверенная матрица вакансий.

Урок: одна тема, простое объяснение, конкретный пример, небольшая задача, review и короткое объяснение на английском B1–B2. По команде «дальше» переходим к следующему шагу. Вопросы разбираем сразу, затем возвращаемся к основной теме.

Агент готовит окружение, каркас и проверки. Учебную логику пользователь пишет сам с подсказками; готовую реализацию агент пишет по прямому запросу. Пройденные темы отличаются от навыков, подтверждённых самостоятельным решением.

Срок: ориентировочно 8–12 недель при 4–6 часах в неделю, с корректировкой после первых лабораторных. Это не гарантия освоения всего стека за фиксированное время.

## Модули и критерии результата

| Модуль | Инструменты и подходы | Практический кейс | Результат и проверка |
|---|---|---|---|
| 0. Рабочая среда | Git, GitHub CLI, Python, uv, pytest, Ruff | Продолжить работу на втором компьютере | Чистый clone, понятные команды запуска и зависимости |
| 1. LLM ingestion | HTTPX, Pydantic, HTTP, async, timeout, retry с backoff и jitter | API возвращает 429, 500, повреждённый ответ или timeout | Mock API + клиент + JSONL; тесты успеха, ошибок и лимита повторов |
| 2. Модель usage и стоимости | Logical request / attempt / event, Decimal, версии тарифов | Повторные попытки и cached tokens искажают расходы | Нормализованная схема и расчёт по синтетическому прайсу; граничные тесты |
| 3. AI observability | OpenTelemetry SDK, Collector, OTLP, trace/span, sampling | LLM ответила, но Collector недоступен | Traces и usage связаны идентификаторами; отдельно проверяем доставку учётных событий |
| 4. Хранение | S3-compatible storage, Parquet, ClickHouse, partitioning | Дубликаты, поздние события и изменение схемы | Raw слой и таблицы; повторная загрузка не удваивает итоговые показатели |
| 5. Пайплайны | Airflow, dbt, incremental models, backfill, SQL quality checks | Переиграть вчерашний день после сбоя | DAG и витрины расходов; проверки уникальности, полноты и свежести |
| 6. AI-инструменты | LiteLLM, Langfuse, structured outputs, tool calling, MCP | Агент вызывает инструмент аналитики расходов | Маленькая интеграция; проверка аргументов, ошибок, trace context и ограничений доступа |
| 7. Оценка качества AI | Набор эталонных примеров, deterministic checks, evals | Ответ корректен по JSON-схеме, но содержит неверный вывод | Воспроизводимый eval dataset; отдельные метрики качества, стоимости и latency |
| 8. Запуск и CI | Docker Compose, GitHub Actions, AWS, Terraform | Новый разработчик запускает demo; CI ловит регрессию | Локальная демонстрация и CI; облачный запуск отдельным этапом с согласованным бюджетом |
| 9. Защита проекта | System design, ADR, runbooks, technical English | Расходы не сходятся с отчётом провайдера | Incident report, reconciliation, демонстрация и объяснение компромиссов |

Версии и способы интеграции сверяем с официальной документацией перед внедрением. Kafka и Spark добавляем при конкретной задаче, требующей streaming или распределённой обработки. RAG, embeddings и vector search — дополнительный модуль после основного MVP, если это подтверждается целевыми вакансиями.

## Первый MVP

1. Mock API возвращает ответ модели, usage и заранее заданные ошибки.
2. Python-клиент измеряет latency, проверяет ответ и ограничивает retries.
3. Схема различает пользовательский запрос, попытку вызова и событие доставки.
4. Валидные события сохраняются в JSONL; некорректные явно отражаются в результате обработки.
5. Тесты воспроизводят успех, 429, 500, timeout, invalid usage и повторную доставку.
6. README описывает запуск и ограничения локального хранения.

Критерий завершения: можно повторить демонстрацию без API-ключей, объяснить происхождение каждого поля и показать обработку сбоя. JSONL — учебный первый шаг; гарантии доставки и восстановления проверим отдельно при добавлении durable pipeline.

## Основные инженерные кейсы

- Timeout после отправки запроса: результат и стоимость неизвестны; повторный вызов может создать дополнительное начисление.
- Повторная доставка одного события: расходы не должны удваиваться.
- Collector или хранилище недоступны: определить очередь, пределы буфера, восстановление и допустимые потери.
- Поздний usage: пересчитать затронутый период и проверить витрины.
- Тариф изменился: сохранить версию расчёта и обеспечить воспроизводимый перерасчёт.
- Reconciliation: сравнить оценку с синтетическим billing export; выявить missing events, caching, retries и разные временные окна.
- Sampling: показать, почему выборка traces не подходит как полный журнал расходов.
- Tool calling: валидный вызов, неверные аргументы и отказ инструмента.

На каждый кейс сохраняем постановку, воспроизведение, решение, тесты, ограничения и короткое объяснение на английском. Учебные инциденты обозначаем как симуляции; измерения производительности публикуем только вместе с параметрами нагрузки.

## Порядок работы и портфолио

Перед работой на другом компьютере — проверить git status и обновить ветку. Изменения делать в небольших ветках codex/*, после проверок — commit и push. Не перезаписывать чужие или незавершённые изменения. После урока обновлять PROGRESS.md: что обсуждали, что реализовано, чем проверено, следующий шаг.

README проекта — на английском; учебные объяснения — на русском. Используем синтетические данные. API-ключи и локальные конфигурации в репозиторий не добавляем.

Финальная демонстрация: запуск с нуля, генерация workload, витрины usage/cost/error rate/p95, один воспроизводимый инцидент, исправление и объяснение архитектуры за 3–5 минут.
